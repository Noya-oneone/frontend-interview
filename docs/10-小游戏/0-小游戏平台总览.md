# 小游戏平台总览

小游戏 = 「小程序容器 + 游戏渲染能力」。和小程序最大的区别：**没有 DOM、没有 WXML/WXSS**，
只给一块 Canvas 和一套宿主 API，页面是自己用 WebGL 画出来的。

## 与 H5 / 小程序 / 原生 App 的定位差异

| 维度 | H5 游戏 | 小游戏（微信/抖音） | 原生 App |
|------|---------|---------------------|----------|
| 运行环境 | 浏览器 | 宿主 JS 引擎 + Canvas | 系统原生 |
| 分发 | URL | 平台内搜索/分享/信息流 | 应用商店下载 |
| 包体限制 | 无（首屏自控） | 主包 4M（微信）/ 全量分包 30M | 上百 M 无压力 |
| 上手成本 | 打开即玩 | 打开即玩 | 需下载安装 |
| 变现 | 自建支付 | 平台内购 + 激励广告 | 内购 + 广告 |
| 审核 | 无 | 有（版号、类目资质） | 有 |

小游戏最大的价值是**零安装转化率**，代价是包体、API 和审核三重约束。

## 主流平台一览

| 平台 | 全局对象 | 引擎构建目标 | 特点 |
|------|----------|--------------|------|
| 微信小游戏 | `wx` | `wechatgame` | 生态最大，社交裂变强，审核最严 |
| 抖音小游戏 | `tt` | `bytedance-mini-game` | 信息流买量强，视频引流，激励广告 eCPM 高 |
| 支付宝小游戏 | `my` | `alipay-mini-game` | 偏轻度、工具向 |
| QQ 小游戏 | `qq` | `wechatgame`（多数兼容） | 年龄层偏低 |
| 快手小游戏 | `ks` | `bytedance-mini-game` 近似 | 与抖音打法相似 |

API 命名高度雷同（`wx.login` / `tt.login`），但**行为和参数并不完全一致**，
这正是跨端适配层存在的意义（见 `3-跨端适配`）。

## 技术栈选择

* **Cocos Creator**：国内小游戏事实标准，官方直接支持各平台构建，编辑器完善，2D/3D 都能做
* **Laya**：早期占有率高，现在生态收缩
* **Egret**：基本退场
* **Unity + WebGL**：包体和首屏内存吃紧，微信有 Unity 转换工具但坑多，重度 3D 才考虑
* **原生 Canvas / Three.js**：轻度小游戏可行，但要自己造资源管理、场景、动画轮子

面试常问「为什么选 Cocos」：**多端构建一键出包 + 资源管理和分包体系成熟 + 中文社区文档全**。

## 一个小游戏的完整生命周期

```
开发（Cocos 编辑器）
  → 构建（Cocos CLI 输出平台工程）
  → 上传（miniprogram-ci / tt CLI）
  → 体验版扫码测试
  → 提审（需软著、游戏版号、类目资质）
  → 发布 → 灰度 → 全量
```

**版号是最大的卡点**：含内购的游戏必须有版号，走完流程常以月计。
纯广告变现的休闲游戏在部分平台可以先上「测试/试玩」类目，但也在逐步收紧。

## 面试高频问题

* 小游戏和小程序的技术差异是什么？（无 DOM、Canvas 渲染、包体限制不同）
* 为什么小游戏首屏要做分包和资源 CDN 化？（主包硬限制 + 首次打开等待时长直接影响留存）
* 怎么做微信和抖音双端复用？（核心逻辑平台无关 + 适配层收口 `wx.` / `tt.`）
