# 小程序

* 背景：微信小程序于2017年9月份正式发布，微信官方推出了小程序的开发工具，并推出了小程序云开发平台，帮助开发者快速搭建小程序。
* 小程序: 微信小程序、支付宝小程序、百度小程序、头条小程序、QQ小程序、快应用、360小程序、快手小程序、抖音小程序、快应用、快应用

* **小程序 VS H5**
  * 更好的性能：小程序运行在原生环境，性能优于 H5。 (基于浏览器内核重构的内置解析器)
  * 更好的用户体验：小程序可以像原生应用一样在桌面创建图标，用户打开速度快，无需下载安装。
  * 更好的功能支持：小程序可以调用更多的设备原生功能，如扫一扫、支付等。
  * 更好的推广效果：小程序可以通过二维码、公众号、朋友圈等多种方式进行推广。
* WXML 标签
* 应用生命周期、页面生命周期、 组件生命周期
* 小程序没有重启的概念，当用户切换到其他应用时，小程序不会被销毁，可以继续运行，这也是小程序的生命周期。
* 小程序进入后台后，客户端会维持一段时间运行状态，超过一定时间后，会被微信主动销毁
* 短时间内收到系统两次以上的内存告警，小程序会进行销毁
* **分包加载**
  * 整个小程序所有分包大小不超过 20M，单个分包/主包大小不能超过 2M
  * 分包是按需加载，即当进入分包的某个页面时，才会下载该分包，对用户流量友好
  * 首页不应放在分包内，会影响首屏加载速度
  * 访问频次高的放主包、访问频次低的放分包
  * 子包预加载技术


## 小程序分包策略
* 项目整体的代码量已经超过`10M`，特别是主包大小一直处在`2M`限制的边缘
* `开启代码压缩` （自动压缩-样式、脚本、WHTML）
* `分包`： 
  * 将非必须存在于主包的代码拆分到相应的分包中，分包`按功能尽可能拆分的小一些`；
  * `非主包`用到的东西不允许放主包，一律放`各个分包`。
* 废弃的代码及时删除，包括js、wxml和样式，`特别是app.wxss`内的样式
* 本地图片替换成`CDN图片`
* wxml结构精简（不要一层一层套用，尽量精简）
* `文件路径压缩`（使用短路径）： 因为文件路径最终会原样打包到代码中，对于代码量很大的项目来说，替换成`更短的路径`也能省不少空间。组件越多、代码目录层级越深，最终的效果越明显。
* `原子css`： 原子css的基本原则，决定了其基础库的大小是固定的，即使同样的css规则被使用了很多次，但其声明只有一次，唯一的弊端是会导致wxml变大，但总体来说代码包大小会下降很多
    * 使用原子化CSS可以让我们不用去考虑CSS类名，不用这个DIV考虑起什么类名，那个SPAN起什么类名，而且能减少代码量，节约写代码的时间，较少包的大小
    * `Taiwind CSS` 原子化CSS
* `类名压缩`： 压缩类名，减少类名长度
* `代码包按需加载，而不是整体加载` 
  * `分包异步化`：  不同的分包对应不同的下载单元，可以按需下载，提高用户体验；
  * 除了非独立分包可以依赖主包外，**分包之间不能互相使用自定义组件或进行 require**
  * `https://developers.weixin.qq.com/miniprogram/dev/framework/subpackages/async.html`

  'preloadRule',
  'subPackages'

## 小程序API做了什么处理，能够做到全局变量的隐藏？

小程序通过模块化、作用域隔离、全局变量管理、页面间数据传递、本地存储、安全隔离以及数据加密等机制，实现了全局变量的有效隐藏和管理。

* 模块化：小程序采用了模块化的设计方式，确保不同的模块或页面拥有自己的作用域
* App 实例的全局变量管理
* 页面传参：小程序允许通过页面跳转传递参数，但这些参数仅在跳转过程中有效，页面关闭后参数不再保留。这种机制避免了全局数据的泄露。
* 本地存储：小程序提供了本地存储 API，如 wx.setStorage() 和 wx.getStorage()，允许将数据存储在本地缓存中
* API 权限：小程序平台对 API 的权限管理非常严格，不同小程序的 API 调用受到限制，避免了数据的跨小程序访问。
* 数据加密：小程序提供了数据加密 API，如 wx.getUserInfo() 和 wx.request()，可以对用户数据进行加密，避免数据泄露。
