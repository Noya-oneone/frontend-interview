# 唤端

## 什么是唤端
* 唤端是指在移动端应用中，用户点击某个按钮或链接后，页面会弹出一个浮层，提示用户进行下一步操作。
* 在Safari浏览器中，当我们点击唤起App按钮后，系统提示我们是否需要 “在app中打开”，点击确认后，App便被唤起来了，这就是一个最简单的唤端场景。
* 唤端的作用
    *  1. 提升用户体验
    *  2. 增加用户黏性
    *  3. 增加用户参与度

## 唤端业务流程
* 对于没有安装相关App的用户，往往会需要跳转到下载页面，让用户去下载App。
* 唤端功能还需要能唤起指定页面，比如一个用户在下单页，唤起App后，我们希望App默认打开的还是那个下单页，不然让用户再走一遍流程到下单页，那对订单转化率会有不小的影响。
```bash
点击唤端（有APP） - 唤起APP - 唤起成功 - 打开指定页面 - 完成操作
点击唤端（有APP） - 唤起APP - 唤起失败 - 打开下载页面 - 下载APP
点击唤端 （没有APP）- 下载APP
```
## 唤端技术架构 （Deep Link（深度链接）技术）

* 1 URL Scheme（全平台通用） 
* 2 Universal Link（通用链接，iOS系统专属）
* 3 App Links 以及衍生的 Chrome Intents（安卓系统专属）

当然，以上是国际通用标准，还需要考虑到的是“国内特色”，包括但不限于微信、微博、UC浏览器等这些环境的唤端，对于这些App，主流的唤端方式有这么几种：
1.  Universal Link（部分App可用，快被国内主流App禁干净了）
2. 微信API launchApplication 和 getInstallState （需要申请白名单，难度很高）
3. 微信开放标签 <wx-open-launch-app> (微信推荐方式，需要审核，流程较繁琐) 
4. 跳转到应用宝，然后通过应用宝唤端 （适用于微信安卓环境）
5.  弹出个蒙层，友好的提示用户，点击右上角按钮，然后选择在浏览器中打开。

### URL Scheme （全平台通用）

我们来看一下 URL 的组成：

`[scheme:][//authority][path][?query][#fragment]`，我们拿 https://www.baidu.com 来举例，scheme 自然就是 https 了。

就像给服务器资源分配一个 URL，以便我们去访问它一样，我们同样也可以给手机APP分配一个特殊格式的 URL，用来访问这个APP或者这个APP中的某个功能(来实现通信)。APP得有一个标识，好让我们可以定位到它，它就是 URL 的 Scheme 部分。

* 使用URL Scheme会遇到一个棘手的问题，那就是**我们无法得知是否成功唤起App**。这个也可以理解，因为这个方式本质上就是访问一个URL，并没有特别的地方。 但是唤端失败（通常是用户没有装这个App），我们需要引导用户去下载，这就要求我们需要通过一些手段，去检测唤端是否成功。

* 常见的做法是通过监听页面是否在 `n秒内 隐藏来判断是否成功唤起App`，因为如果唤起，那当前页面必然已经退到后台去了。 所以我们处理的流程是这样 
    * 1. 当点击唤端后，定时器延时n秒(我们设定的是`2.5秒`)后执行跳转操作 
    * 2. 监听 `visibilitychange 事件`，如果页面隐藏，则表示唤端成功，清除定时器 
    * 3. 如果 `visibilitychange 事件没有被触发，那么就代表唤端失败`，n秒后就会执行跳转落地页的操作：
* 不过这个方法有个致命问题，就是 n 应该取多少，不同的手机，唤端的时间并不一样。 （当业务需求要求自动下载时）
    * 时间设置太长，用户下载等待太久，会导致用户还没看到下载就退出了。 
    * 时间设置太短，可能会导致还没有唤起App，就又同时执行了下载的逻辑。
    * 这里通过调研，**n设置为2500ms-3000ms**，是一个比较合适的值。

#### URL Scheme在iOS上的问题
    上面说到了唤端失败跳转到下载落地页的场景。在实际项目中，我们会发现在iOS上使用URL Scheme还有一个问题，就是即执行了唤起，也执行了跳转下载落地页。经过测试我们得到了如下流程 
    1. 用户点击唤端按钮（记录time1） 
    2. Safari弹出是否在app打开的confirm框, 此时虽然弹出了alert框，但是并未阻断代码运行，所有代码仍在运行中，只是界面没变 
    3. 用户点击打开app（记录time2），跳转到app
    4. 用户返回Safari，如果time2 - time1的时间大于设置的时间 n，那么之前的逻辑代码便会继续运行。也就会出现唤端成功后，又继续走跳转逻辑

```bash
     行为(应用的某个功能)    
            |
scheme://[path][?query]
   |               |
应用标识       功能需要的参数

getguang://guang//native route
```

```js
// SCHEMA_PATH 为 URL Scheme 地址

// location.href 形式
window.top.location.href = SCHEMA_PATH;

// a标签形式
const a = document.createElement("a");
a.setAttribute("href", SCHEMA_PATH);
a.click();

// iframe形式
iframe = document.createElement('iframe');
iframe.frameBorder = '0';
iframe.style.cssText = 'display:none;border:0;width:0;height:0;';
document.body.append(iframe);
iframe.src = SCHEMA_PATH;
```

```js

// n秒后执行下载
const timer = setTimeout(() => {
    this.download(options);
}, options.delay);

// 页面隐藏，那么代表已经调起了app，就清除下载的定时器
const visibilitychange = function() {
    const tag = document.hidden || document.webkitHidden;tag && clearTimeout(timer);
};
document.addEventListener("visibilitychange", visibilitychange, false);

document.addEventListener("webkitvisibilitychange", visibilitychange, false);

window.addEventListener("pagehide",function() {
    clearTimeout(timer);
},false);

// visibilitychange当然这个事件是有兼容性的，具体的代码实现时做了事件是否需要添加前缀（比如 -webkit- ）的校验。如果都不兼容，我们将使用 pagehide 事件来做兜底处理。
```

### Universal Link （苹果IOS）

Universal Link 是 iOS 9 引入的新特性，可以让我们在 iOS 设备上打开 App 或者 App 中的某个功能，而无需在 Safari 中打开。

它与 URL Scheme 的区别在于，它是通过系统的设置来实现的，不需要我们自己去写代码。我们只需要在 Xcode 中配置好 Associated Domains，然后在 App Store Connect 中配置好 Universal Links，就可以实现唤端功能。

#### 传统的 Scheme 链接有以下几个痛点：
* 在 ios 上会有确认弹窗提示用户是否打开，对于用户来说唤端，多出了一步操作。若用户未安装 APP ，也会有一个提示窗，告知我们 “打不开该网页，因为网址无效”
* 传统 Scheme 跳转无法得知唤端是否成功，Universal Link 唤端失败可以直接打开此链接对应的页面
* Scheme 在微信、微博、QQ浏览器、手百中都已经被禁止使用，使用 Universal Link 可以避开它们的屏蔽（ 截止到 18年8月21日，微信和QQ浏览器已经禁止了 Universal Link，其他主流APP未发现有禁止 ）

### App Links && Chrome Intents （安卓Android）

* AppLinks使用和Universal Link 用法一致
* App Links 是 Android 系统中引入的新特性，可以让我们在 Android 设备上打开 App 或者 App 中的某个功能，而无需在 Chrome 浏览器中打开。
* 每个APP都希望被自己制定的scheme唤起，这就是Applink，之前分析deeplink的时候提到了ResolveActivity这么一个选择过程，而AppLink就是自动帮用户完成这个选择过程，并且选择的scheme是最适合它的scheme（开发者的角度）。因此对于AppLink要分析的就是如何完成了这个默认选择的过程。

#### intent (安卓)
* 安卓的原生谷歌浏览器自从 chrome25 版本开始对于唤端功能做了一些变化，URL Scheme 无法再启动Android应用。 例如，通过 iframe 指向 weixin://，即使用户安装了微信也无法打开。所以，APP需要实现谷歌官方提供的 intent: 语法
* 它与 URL Scheme 的区别在于，它是`通过 Chrome 浏览器的插件来实现的`，不需要我们自己去写代码。我们只需要在 Chrome 插件中配置好 intent-filter，就可以实现唤端功能。

```bash
intent:
   HOST/URI-path // Optional host 
   #Intent; 
      package=[string]; 
      action=[string]; 
      category=[string]; 
      component=[string]; 
      scheme=[string]; 
   end;
   // 如果用户未安装 APP，则会跳转到系统默认商店。当然，如果你想要指定一个唤起失败的跳转地址，添加下面的字符串在 end; 前就可以了:
   S.browser_fallback_url=[encoded_full_url]
   
   // demo
   //下面是打开 Zxing 二维码扫描 APP 的 intent。
   intent:
   //scan/
   #Intent; 
      package=com.google.zxing.client.android; 
      scheme=zxing; 
   end; 
   // 打开app
    <a href="intent://scan/#Intent;scheme=zxing;package=com.google.zxing.client.android;S.browser_fallback_url=http%3A%2F%2Fzxing.org;end"> Take a QR code </a>
```

### 开箱即用的callapp-lib
 npm 包 callapp-lib 是一个开箱即用的唤端库，它可以帮助我们快速实现唤端功能，并提供一些默认的配置，让我们可以快速上手。

#### 安装
```bash
npm install callapp-lib --save
```

#### 使用
```js
import CallApp from 'callapp-lib';

const callApp = new CallApp({
    scheme: 'your-scheme', // 唤端的scheme
    packageName: 'your-package-name', // 唤端的包名
    downloadUrl: 'your-download-url', // 唤端失败的下载地址
    delay: 2500, // 唤端成功后的延时时间
    success: () => {
        console.log('唤端成功');
    },
    fail: () => {
        console.log('唤端失败');
    }
});

// 唤端
callApp.call();
```

#### 配置项
* scheme: 唤端的scheme
* packageName: 唤端的包名
* downloadUrl: 唤端失败的下载地址
* delay: 唤端成功后的延时时间
* success: 唤端成功的回调函数
* fail: 唤端失败的回调函数

#### 注意事项
* 唤端成功后的延时时间，默认设置为 2500ms，如果业务需求要求自动下载，可以适当调整。
* 唤端失败的下载地址，默认设置为 https://www.baidu.com，如果业务需求要求自定义下载地址，可以修改。
* 唤端失败的回调函数，默认会打开浏览器，并跳转到 downloadUrl 地址，如果业务需求要求自定义失败后的操作，可以修改。
