# 怎么设计一个沙盒

沙盒（Sandbox）就是`给不受信任的代码一个隔离的运行环境`，让它跑得起来，但碰不到不该碰的东西。

前端遇到沙盒的三个典型场景：

* **微前端**：多个子应用共用一个 `window`，A 应用改了 `window.axios`，B 应用跟着崩（qiankun 的 JS 沙箱解决的就是这个）
* **在线代码编辑器**：CodeSandbox、掘金码上掘金，要执行用户输入的任意 JS
* **插件 / 低代码平台**：执行第三方提交的脚本、模板表达式

设计沙盒先问两个问题：`要隔离什么`（全局变量？DOM？网络？）、`能接受多大代价`（性能、通信复杂度）。没有万能方案，下面四种按隔离强度从弱到强排。

## 方案一：快照沙箱（Snapshot）

最朴素的思路：`进入前拍照，退出时还原`。

```javascript
class SnapshotSandbox {
  constructor() {
    this.modifyMap = {};   // 记录被修改的属性
    this.windowSnapshot = {};
  }

  active() {
    // 1. 保存当前 window 的所有属性
    this.windowSnapshot = {};
    for (const prop in window) {
      this.windowSnapshot[prop] = window[prop];
    }
    // 2. 恢复上次退出时记录的修改
    Object.keys(this.modifyMap).forEach(p => {
      window[p] = this.modifyMap[p];
    });
  }

  inactive() {
    for (const prop in window) {
      if (window[prop] !== this.windowSnapshot[prop]) {
        // 3. 记录变更，并还原 window
        this.modifyMap[prop] = window[prop];
        window[prop] = this.windowSnapshot[prop];
      }
    }
  }
}
```

**缺点很明显**：

* 要遍历整个 `window`，属性上千个，`性能差`
* 本质是`还原`不是`隔离` —— 子应用运行期间污染依然真实发生在 window 上
* `只支持单实例`，两个子应用同时运行就互相覆盖

qiankun 里这是`降级方案`，只在不支持 Proxy 的浏览器（IE）用。

## 方案二：Proxy 代理沙箱（主流）

用 `Proxy` 造一个假的 `window`，读的时候优先读自己的、找不到再去真 window 找；`写的时候只写进自己的副本，永不污染真 window`。

```javascript
class ProxySandbox {
  constructor(name) {
    this.name = name;
    this.running = false;
    const fakeWindow = Object.create(null);   // 子应用的私有空间

    this.proxy = new Proxy(fakeWindow, {
      get: (target, prop) => {
        // 防止子应用通过 window.window 逃逸出去
        if (prop === 'window' || prop === 'self' || prop === 'globalThis') {
          return this.proxy;
        }
        if (prop in target) return target[prop];

        const value = window[prop];
        // 原生方法必须绑回 window，否则 this 指向 fakeWindow 会报 Illegal invocation
        return typeof value === 'function' && !value.prototype
          ? value.bind(window)
          : value;
      },

      set: (target, prop, value) => {
        if (this.running) target[prop] = value;   // 只写副本
        return true;
      },

      has: (target, prop) => prop in target || prop in window,

      // with 语句会查 Symbol.unscopables，必须处理
      getOwnPropertyDescriptor: (target, prop) => {
        if (prop in target) return Object.getOwnPropertyDescriptor(target, prop);
        return Object.getOwnPropertyDescriptor(window, prop);
      }
    });
  }

  active()   { this.running = true; }
  inactive() { this.running = false; }
}
```

配合 `with` 把子应用代码的作用域顶替掉：

```javascript
function runCode(code, proxy) {
  // with 让代码里裸写的 axios 先去 proxy 上找，而不是直接命中真 window
  const wrapped = `
    (function(window, self, globalThis) {
      with (window) { ${code} }
    })
  `;
  // 用 eval 而非 new Function，才能拿到闭包里的 proxy
  return eval(wrapped)(proxy, proxy, proxy);
}

const sandboxA = new ProxySandbox('appA');
sandboxA.active();
runCode('window.foo = 1; console.log(foo)', sandboxA.proxy);

window.foo;              // undefined ✅ 真 window 没被污染
sandboxA.proxy.foo;      // 1
```

**优点**：真正的隔离、`支持多实例并存`（每个子应用一个 proxy），性能远好于快照。

**这是 qiankun `LegacySandbox` / `ProxySandbox` 的核心思路。**

### 几个必踩的坑

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| 原生方法 this 丢失 | `alert is not a function` / `Illegal invocation` | get 时 `value.bind(window)` |
| `window.window` 逃逸 | 子应用拿 `window.window.foo` 摸到真 window | get 拦截 `window`/`self`/`globalThis` 返回 proxy |
| `with` 的 unscopables | 变量意外穿透到外层 | 实现 `has` 恒返回 true 或处理 `Symbol.unscopables` |
| 构造函数被 bind | `new window.Image()` 报错 | 用 `value.prototype` 判断，有原型的不 bind |

## 方案三：iframe 天然隔离

浏览器`原生提供`的隔离边界 —— 每个 iframe 有独立的 `window`、`document`、事件循环和 JS 上下文。

```html
<!-- sandbox 属性是权限白名单，不写任何值 = 全部禁止 -->
<iframe
  src="/plugin.html"
  sandbox="allow-scripts"
></iframe>
```

`sandbox` 常用取值：

| 值 | 含义 |
| --- | --- |
| `allow-scripts` | 允许执行 JS |
| `allow-same-origin` | 允许被视为同源（`慎用`） |
| `allow-forms` | 允许提交表单 |
| `allow-popups` | 允许 window.open |
| `allow-top-navigation` | 允许跳转顶层页面 |

> ⚠️ `allow-scripts` 和 `allow-same-origin` `同时开启等于沙箱失效` —— 里面的脚本可以直接删掉自己的 sandbox 属性再重载，逃逸出来。

**优点**：隔离最彻底，连 DOM、cookie、localStorage 都隔开。
**缺点**：通信只能靠 `postMessage`（异步、要序列化）；URL / 路由不同步；弹窗被限制在 iframe 内部；每个 iframe 都要重新加载一套资源，`内存和性能开销大`。

```javascript
// 父 → 子
iframe.contentWindow.postMessage({ type: 'INIT', data }, 'https://trusted.com');

// 子 → 父，必须校验来源，否则任意页面都能给你发消息
window.addEventListener('message', e => {
  if (e.origin !== 'https://trusted.com') return;   // ✅ 安全关键
  handle(e.data);
});
```

## 方案四：Web Worker（计算型沙盒）

Worker 里`没有 window、没有 document`，天然碰不到 DOM，适合执行纯计算型的不可信代码。

```javascript
const worker = new Worker(
  URL.createObjectURL(new Blob([`
    self.onmessage = e => {
      // 这里没有 DOM 可以碰
      const result = eval(e.data);
      self.postMessage(result);
    };
  `]))
);

worker.postMessage('1 + 1');
worker.onmessage = e => console.log(e.data);   // 2

// 超时强杀，防止死循环把线程占满
setTimeout(() => worker.terminate(), 3000);
```

**优点**：不阻塞主线程，`可以强制终止`（这点 Proxy 沙箱做不到 —— 子应用写个 `while(true)` 就把页面卡死了）。
**缺点**：不能操作 DOM，只能做计算。

## 横向对比

| 方案 | 隔离强度 | 性能 | 多实例 | 能否操作 DOM | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| 快照 | 弱（事后还原） | 差 | ❌ | ✅ | IE 降级 |
| Proxy | 中（JS 变量级） | 好 | ✅ | ✅ | 微前端 |
| iframe | 强（进程/上下文级） | 差 | ✅ | ✅（自己的） | 插件、第三方页面 |
| Worker | 强（无 DOM） | 好 | ✅ | ❌ | 在线执行代码 |

## 别忘了 CSS 隔离

JS 沙箱只管变量，`样式污染要单独处理`：

* **Shadow DOM**：`el.attachShadow({ mode: 'open' })`，浏览器原生隔离，但第三方组件库的弹窗挂到 body 上就漏出去了
* **动态改写选择器**：qiankun 的 `experimentalStyleIsolation`，给所有规则加 `div[data-qiankun="appA"]` 前缀
* **CSS Modules / BEM 命名约定**：编译期方案，靠约定不靠运行时

## 常见追问

**Q：Proxy 沙箱能防住恶意代码吗？**
`不能`。它是为了`防冲突`不是`防攻击`。子应用完全可以通过 `document.body`、`(function(){return this})()`、`Function('return this')()` 等方式摸到真实全局对象。真要防恶意代码，必须用 iframe（`不带 allow-same-origin`）或 Worker，靠浏览器的安全边界。

**Q：为什么用 `eval` 而不是 `new Function`？**
`new Function` 的作用域链只到全局，拿不到外层闭包里的 `proxy` 变量；`eval` 在当前词法作用域执行，才能让 `with(window)` 里的 `window` 指向我们传入的 proxy。

**Q：怎么处理子应用的定时器和事件监听？**
子应用卸载时如果不清理，`setInterval` 和全局事件监听会一直跑，造成内存泄漏。做法是`劫持 setTimeout / setInterval / addEventListener`，把创建的 id 和 handler 记在沙箱实例上，`inactive()` 时统一清除：

```javascript
const timers = [];
proxy.setInterval = (...args) => {
  const id = window.setInterval(...args);
  timers.push(id);
  return id;
};
// 卸载时
inactive() { timers.forEach(clearInterval); timers.length = 0; }
```

**Q：qiankun 到底用了哪种？**
按浏览器能力降级：支持 Proxy 且是`单实例` → `LegacySandbox`（只记录 3 类变更，比全量 diff 快）；`多实例` → `ProxySandbox`；不支持 Proxy → `SnapshotSandbox`。CSS 侧默认用 HTML Entry 天然作用域 + 可选的 `strictStyleIsolation`（Shadow DOM）。
