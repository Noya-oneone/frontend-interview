# TCP 三次握手/四次挥手 & 输入 URL 后发生了什么

## 输入 URL → 页面展示 全流程

1. **URL 解析**：判断是搜索词还是地址；检查 HSTS 决定是否强制 HTTPS。
2. **DNS 解析**：域名 → IP（缓存逐级查找：浏览器 → 系统 → 本地 DNS → 根/顶级/权威，见 [网络协议](./6-网络协议.md)）。
3. **TCP 连接**：三次握手（HTTPS 再加 TLS 握手，见 [HTTPS](./5.1-Http%20&%20HTTPS.md)）。
4. **发送 HTTP 请求**：请求行 + 请求头 + 空行 + 请求体。
5. **服务器处理并响应**：网关/负载均衡 → 应用服务 → 返回状态码与响应体。
6. **浏览器解析渲染**：HTML → `DOM 树`，CSS → `CSSOM`，合成`渲染树` → 布局（Layout）→ 绘制（Paint）→ 合成上屏（详见 [加载时间线](../2-JS/21-加载时间线.md)）。
7. **连接关闭或复用**：keep-alive 复用连接，最终四次挥手关闭。

### 重排与重绘

* `重排（Reflow，即回流）`：几何属性变化（宽高、位置）→ 重新计算布局，代价大。
* `重绘（Repaint）`：只改外观不改布局（颜色、背景）→ 重新绘制。重排必然引起重绘，反之不然。

## 三次握手（建立连接）

| 步 | 动作 | 状态变化 |
|--|--|--|
| 1 | 客户端发 `SYN`（带初始序列号） | 客户端 → SYN_SENT |
| 2 | 服务器回 `SYN + ACK`（确认客户端序号 + 自己的序号） | 服务器 → SYN_RCVD |
| 3 | 客户端回 `ACK` | 双方 → ESTABLISHED |

**为什么是三次而不是两次？**（必考）确认`双方的收发能力都正常`并同步初始序列号：两次握手时，服务器无法确认自己的 SYN 被收到；且历史延迟的 SYN 到达会让服务器白建连接。

> 类比打电话：「听得到吗？」「听得到，你呢？」「我也听到了」—— 然后才开始正式对话。

## 四次挥手（释放连接）

| 步 | 动作 | 说明 |
|--|--|--|
| 1 | 主动方发 `FIN` | 我没有数据要发了 |
| 2 | 被动方回 `ACK` | 知道了（但我可能还有数据没发完） |
| 3 | 被动方发 `FIN` | 我也发完了 |
| 4 | 主动方回 `ACK`，进入 `TIME_WAIT` | 等 2MSL 后关闭 |

**为什么挥手要四次？** 因为 TCP 全双工：`ACK 和 FIN 不能合并` —— 收到对方 FIN 时己方可能还有数据要发，先 ACK 确认、发完数据再发自己的 FIN。

**TIME_WAIT 为什么等 2MSL？** 确保最后的 ACK 若丢失、对方重发 FIN 时还能应答；并让旧连接的报文在网络中自然消亡，避免污染新连接。

## 浏览器 TCP 并发连接限制

* HTTP/1.1 下每个域名并发约 `6 个连接`（Chrome/Firefox/Edge 均为 6），这是雪碧图、域名分片等老优化的由来。
* HTTP/2 起单域名`一条连接多路复用`，此限制不再是瓶颈（见 [HTTP 版本演进](./5-%20应用层%20HTTP1.0%20%20&%20HTTP2.0%20&%20HTTP3.0.md)）。
