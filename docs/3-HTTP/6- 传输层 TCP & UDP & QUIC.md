# 传输层：TCP & UDP & QUIC

## TCP vs UDP

| 特性 | TCP | UDP |
|--|--|--|
| **连接** | `面向连接`：三次握手建立、四次挥手释放 | `无连接`：拿起来就发 |
| **可靠性** | 可靠：确认、超时重传、按序交付 | 不可靠：丢了就丢了，不重传 |
| **数据形态** | `面向字节流`：无消息边界，应用层需自己拆包/粘包处理 | `面向报文`：保留消息边界，一个报文一个包（单个报文最大约 64KB） |
| **流量/拥塞控制** | 都有（滑动窗口 / 慢启动等） | 都没有，发多快由应用决定 |
| **头部开销** | 至少 20 字节 | 8 字节 |
| **速度** | 较慢（握手 + 确认重传 + 拥塞退让） | 快、延迟低 |
| **场景** | 网页、API、文件传输、邮件 —— `正确性优先` | 音视频通话、直播、游戏、DNS —— `实时性优先，容忍少量丢失` |

要点展开：

* **可靠性代价**：TCP 丢包时按序交付机制会让后续数据等待重传（队头阻塞）；UDP 不保证到达与顺序，但一个包的丢失不影响其他包。
* **粘包问题**（TCP 特有考点）：字节流没有边界，连续 send 的两条消息可能被一次 recv 读到 —— 应用层需用「长度前缀 / 分隔符」定界；UDP 天然无此问题。

## UDP vs QUIC

QUIC 是`构建在 UDP 之上的可靠传输协议`，把 TCP 的可靠性、TLS 加密、HTTP/2 的多路复用整合进一层：

| 特性 | UDP | QUIC |
|--|--|--|
| 可靠性 | 无 | 有（确认与重传，`按流独立`） |
| 连接建立 | 无 | 1-RTT（会话复用 `0-RTT`），握手与 TLS 1.3 合并 |
| 加密 | 无 | `内建强制加密` |
| 多路复用 | 无 | 多流并发，`一个流丢包不阻塞其他流`（解决 TCP 队头阻塞） |
| 连接迁移 | — | 支持：连接以 Connection ID 标识而非四元组，`WiFi ↔ 蜂窝切换不断连` |

HTTP/3 = HTTP over QUIC（见 [HTTP 版本演进](./5-%20应用层%20HTTP1.0%20%20&%20HTTP2.0%20&%20HTTP3.0.md)）。

## 常见考点

* **为什么 DNS 用 UDP？** 查询报文小、一问一答，UDP 免握手延迟低；响应超过限制或区域传输时回退 TCP。
* **视频通话为什么不用 TCP？** 重传来的旧帧已无意义，宁可丢帧也不要卡顿；RTC 在 UDP 上自己做选择性重传与抗抖动。
* **QUIC 为什么选择 UDP 而不是新传输协议？** 中间设备（NAT、防火墙）只认 TCP/UDP，新协议无法穿透部署；UDP 之上用户态实现还能快速迭代（不依赖操作系统内核升级）。
