# API 请求签名过程

## 为什么要签名

开放接口需要防三件事：`身份伪造`（请求真是这个调用方发的吗）、`参数篡改`（传输中被改过吗）、`重放攻击`（旧请求被截获重发）。签名（HMAC）+ 时间戳 + 随机数是标准解法。

## 客户端签名流程

1. **构造待签名字符串（canonical string）**：把关键要素按`固定顺序`拼接 —— 通常包括：
   * HTTP 方法（GET/POST...）
   * 请求路径（URI）
   * `排序后的查询参数/业务参数`（按 key 字典序，避免顺序不同导致签名不一致）
   * 关键请求头（如 Content-Type、Date）
   * 时间戳 `timestamp` 与随机数 `nonce`（防重放）
2. **计算签名**：用`双方共享的密钥（secret）`对字符串做 `HMAC-SHA256`（而不是裸哈希 —— 裸 MD5/SHA 没有密钥，任何人都能算，起不到认证作用）：

```ts
import { createHmac } from 'crypto';

function sign(secret: string, method: string, path: string, params: Record<string, string>) {
  const sorted = Object.keys(params).sort().map(k => `${k}=${params[k]}`).join('&');
  const stringToSign = [method.toUpperCase(), path, sorted].join('\n');
  return createHmac('sha256', secret).update(stringToSign).digest('hex');
}
```

3. **随请求发送**：签名与元信息放进请求头（如 HTTP Signatures 规范格式）：

```
Authorization: Signature keyId="your-key-id",algorithm="hmac-sha256",
               headers="(request-target) date content-type",signature="<签名值>"
```

（keyId 标识用哪把密钥；secret 本身`绝不随请求传输`。）

## 服务端验签流程

1. 解析出 keyId、算法、参与签名的字段与签名值。
2. 按 keyId 查出对应 secret，用`相同规则重新构造字符串并计算 HMAC`。
3. 比对签名（用恒定时间比较防时序攻击）。
4. 校验 `timestamp 在允许窗口内`（如 ±5 分钟）且 `nonce 未出现过`（Redis 记录）→ 防重放。

任何一步失败即拒绝（401/403）。

## 常见考点

* **为什么参数要排序？** 保证同一组参数在两端生成`完全一致`的待签名串 —— 序列化不确定性是签名对不上的头号原因。
* **HMAC 和「MD5 加盐」的区别？** HMAC 是有密钥的标准 MAC 构造，安全性有证明；简单拼接盐再哈希存在长度扩展攻击等风险。MD5 已不建议用于任何安全场景。
* **签名和 HTTPS 重复吗？** 不重复：HTTPS 保证`传输通道`安全，签名保证`调用方身份与参数完整性`（防内部越权调用、网关后明文段篡改），开放平台通常两者都要。
* **前端（浏览器）能做请求签名吗？** secret 放前端等于公开，只能做弱校验；真正的签名应在服务端/BFF 完成，浏览器侧靠 Cookie/token 认证。
