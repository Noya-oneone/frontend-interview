
# 内网

## 网关层 - 系统的守门人
* 是位于客户端和后端服务之间的中间层
* 作为请求的入口点，负责将客户端的请求路由到适当的后端服务，并将后端服务的响应返回给客户端
* 网关层主要负责处理一些通用的横切关注点，如路由、安全、监控和限流等，为后端服务提供统一的入口和保护
  
## 聚合 / 适配层 （ BFF 层） - 桥梁和业务协调者
* 聚合 / 适配层也称为 BFF（Backend for Frontend）
* 主要承担适配角色，将内部复杂的微服务，适配成对各种不同用户体验（如无线、Web、H5、第三方等）友好和统一的 API
* 针对不同客户端的需求，对后端微服务进行业务逻辑的编排和数据的适配，提供更符合客户端期望的 API

## 微服务 Micro Services

* **独立自治**：每个微服务都有自己独立的代码库、数据库和运行环境，能够独立进行开发、测试、部署和升级，不会因为其他微服务的变化而受到影响。这使得不同的团队可以专注于不同的微服务，提高开发效率和软件的可维护性
* **故障隔离性**：当某个微服务出现故障时，只会影响到该微服务本身，不会导致整个系统崩溃。其他微服务仍然可以正常运行，从而提高了系统的可靠性和稳定性。同时，由于微服务的独立性，故障的排查和修复也更加容易。
* **细粒度划分**：微服务架构将大型应用程序按照业务功能划分为多个细粒度的服务，每个服务都具有明确的职责和功能边界。例如，在一个电商系统中，可能会有用户管理微服务、商品管理微服务、订单管理微服务、支付微服务等，每个微服务只负责处理与其相关的业务逻辑。
* **轻量级通信**：微服务之间通过轻量级的通信机制进行交互，通常使用 HTTP/RESTful API 或者消息队列等方式。这种通信方式简单灵活，能够方便地实现不同微服务之间的协作和数据共享。
* **可扩展性**：由于每个微服务都是独立的，可以根据业务需求对单个微服务进行水平扩展，即增加服务实例的数量来处理更多的请求。例如，在电商促销活动期间，订单管理微服务可能会面临大量的订单请求，可以通过增加订单管理微服务的实例数量来提高系统的处理能力，而不需要对整个系统进行大规模的调整。
* **技术多样性**：在微服务架构中，不同的微服务可以根据其具体的业务需求选择合适的技术栈。例如，对于数据处理量较大的微服务，可以选择使用高性能的数据库和计算框架；对于实时性要求较高的微服务，可以采用消息队列和流计算技术。这种技术多样性使得开发团队能够根据实际情况选择最适合的技术，充分发挥各种技术的优势。
