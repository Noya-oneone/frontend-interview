# 丢包与 408 超时

## 什么是丢包

数据包在传输途中未能到达接收端（或校验失败被丢弃）。`网络拥塞是丢包的最主要原因`（路由器/交换机缓冲区满而丢弃），此外还有链路质量差（弱网、Wi-Fi 干扰）、防火墙拦截、设备故障等。注意因果方向：**拥塞导致丢包，丢包率又是拥塞控制的信号** —— TCP 检测到丢包会主动降速。

## 各层如何应对

* **TCP 自动处理**：确认 + 超时重传 + 快速重传机制，应用层通常无感知，只表现为`变慢`。
  * 代价：重传与按序交付造成队头阻塞、拥塞窗口收缩 —— 高丢包率下 TCP 吞吐急剧下降。
* **UDP 不处理**：应用层自行取舍（音视频宁丢勿卡，或像 QUIC 一样自建重传，见 [TCP & UDP & QUIC](./6-%20传输层%20TCP%20&%20UDP%20&%20QUIC.md)）。
* **应用层兜底**：
  * `超时 + 重试`：请求失败自动重试，配`指数退避`避免雪崩。
  * `心跳机制`：长连接（WebSocket）定期心跳，超时未响应判定断线并重连。
  * `幂等设计`：重试的前提 —— GET 天然幂等，写操作需幂等键防重复提交。

## 与丢包相关的状态码

| 状态码 | 场景 |
|--|--|
| `408 Request Timeout` | 客户端`没能在服务器时限内发完请求`（弱网上传大文件、请求发一半断了） |
| `504 Gateway Timeout` | 网关等`上游服务`响应超时 |
| （无状态码，请求直接失败） | 连接层面超时/断开时拿不到任何响应，前端表现为 fetch 抛 TypeError / timeout |

## 前端实践

```ts
async function fetchWithRetry(url: string, retries = 3, timeout = 5000): Promise<Response> {
  for (let i = 0; i <= retries; i++) {
    try {
      const res = await fetch(url, { signal: AbortSignal.timeout(timeout) });
      if (res.ok) return res;
      if (res.status < 500) return res;        // 4xx 不重试
    } catch (err) {
      if (i === retries) throw err;
    }
    await new Promise(r => setTimeout(r, 2 ** i * 1000)); // 指数退避：1s/2s/4s
  }
  throw new Error('unreachable');
}
```

## 常见考点

* **弱网优化思路？** 减少请求数与体积（合并、压缩、缓存）、重试与降级策略、HTTP/3（QUIC 抗丢包更好）、离线缓存（Service Worker）。
* **怎么判断用户网络质量？** `navigator.connection`（effectiveType/rtt/downlink）、请求耗时统计上报。
