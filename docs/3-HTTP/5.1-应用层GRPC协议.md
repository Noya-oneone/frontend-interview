# 应用层 gRPC 协议

## 是什么

* gRPC 是 Google 开源的高性能 `RPC 框架`：客户端`像调用本地函数一样`调用远程服务的方法，不必关心底层网络细节。
* 两大支柱：
  * `Protobuf`（Protocol Buffers）：接口定义语言（IDL）+ 二进制序列化格式 —— 先写 `.proto` 定义服务与消息，再生成各语言的客户端/服务端代码；`强类型、体积小、编解码快`（相较 JSON）。
  * `HTTP/2` 传输：复用其`多路复用、头部压缩、双向流`能力，一个连接并发多个调用。

```protobuf
service UserService {
  rpc GetUser (GetUserRequest) returns (User);
  rpc WatchUsers (WatchRequest) returns (stream User);  // 服务端流
}
```

## 四种调用模式

| 模式 | 形态 | 场景 |
|--|--|--|
| Unary | 一问一答 | 普通接口调用 |
| Server streaming | 一问多答 | 实时行情推送、日志流 |
| Client streaming | 多问一答 | 批量上传、汇总统计 |
| Bidirectional streaming | 双向流 | IM、实时协作 |

## gRPC vs REST（高频对比）

| | gRPC | REST/JSON |
|--|--|--|
| 载荷 | Protobuf 二进制，小而快 | JSON 文本，可读性好 |
| 契约 | .proto 强约束，代码生成 | OpenAPI 文档约定，弱约束 |
| 浏览器 | 不能直接调用（浏览器无法控制 HTTP/2 帧），需 `gRPC-Web` + 代理转换 | 原生支持 |
| 典型位置 | `微服务之间`的内部通信 | 对外开放 API、浏览器前端 |

## 常见考点

* **前端能直接用 gRPC 吗？** 浏览器端需要 gRPC-Web（配合 Envoy 等代理做协议转换）；常见架构是「浏览器 ⇄ REST/BFF ⇄ 内部 gRPC 微服务」。
* **为什么内部服务偏爱 gRPC？** 强类型契约减少联调歧义、二进制序列化省带宽 CPU、原生流式支持、多语言代码生成。
