# RestFul & GraphQL

## 规范格式而已

* **RESTful API**： `服务端决定返回什么数据`、可以使用 HTTP 状态码来表示错误
    * 使用固定的 HTTP 方法：GET、POST、PUT、DELETE
    * 基于 HTTP 的 API 风格，通过资源的 URL 进行交互
    * 通过多个端点获取数据，每个端点提供不同的资源 
    * 可能会返回多余的数据（例如，获取的字段不全）
    * 通常需要版本控制（如 /api/v1/） 綁定
    * 支持缓存（通过 HTTP 缓存机制）
    * 固定的响应格式，通常是 JSON 或 XML
* **GraphQL：**： `客户端决定返回什么数据，服务端只提供接口`，客户端通过查询语句来获取数据，可以**灵活的查询数据**，可以缓存数据，可以订阅数据变化、每个请求都会返回 200 OK 状态码，错误信息会包含在响应体中
    * 单一 POST 请求，通过查询字符串定义请求
    * 一种查询语言和运行时，用于获取和操作数据 
    * 单个端点，通过查询字段选择需要的数据
    * 精确指定需要的字段，仅获取所需的数据
    * 缓存较复杂，通常需要额外配置（传统的 HTTP 缓存机制（如 Cache-Control 和 ETag）不太适用）
        * 一些优化手段可以使其利用 HTTP 缓存。例如，通过将 GraphQL 查询转换为 GET 请求，并使用查询字符串来表示不同的查询和变量组合。
        
     * Apollo Client 和 Relay：GraphQL 的客户端库（如 Apollo Client 和 Relay）内置了智能缓存机制。
         * 它们会基于查询的结构和变量，对每个请求的结果进行缓存，并在后续请求中使用缓存的结果。
         * 去重和合并请求：这些客户端库还可以在多个组件请求相同数据时自动去重和合并请求，以减少不必要的网络请求。
  
* **缓存部分字段**：如果某些字段频繁变化而其他字段比较稳定，可以选择只缓存稳定的字段。
* **版本化缓存**：通过给查询增加版本信息，每次请求时根据版本号来判断是否使用缓存。

    * 无需版本控制，客户端请求可以动态变化
    * 灵活的响应格式，根据查询返回所需数据
    * 緩存器，识别Header - 参数 一个端口Client ， 其他都放在参数层
    * restful post get 各种请求 明确的，方便做缓存，单一设计，只做一件事情
    * graphQL  一个接口做N多事情，识别参数， 做缓存比较复杂

## 详细比较

### RESTful API
- **优点**：
- 简单易懂，`符合 HTTP 协议的原生操作`。
- 有广泛的支持和成熟的工具。
- 适用于标准化的资源操作和 `CRUD（创建、读取、更新、删除）操作`。
- `缓存机制简单，可以利用 HTTP 缓存头部减少服务器负担`。

- **缺点**：
- 请求可能会导致过多的数据传输或请求次数，特别是在复杂的嵌套数据场景下。
- 需要处理版本控制，可能导致 API 设计和维护的复杂性。
- 数据获取不够灵活，可能会返回不需要的数据或需要多次请求。

### GraphQL
- **优点**：
- 单个请求可以获取所有所需的数据，`减少了请求次数和数据传输量`。
- 客户端可以精确指定需要的数据字段，`减少不必要的数据传输`。
- `不需要版本控制`，通过查询和变更来管理数据结构。
- 提供强大的类型系统和`自文档化能力`，易于自动生成文档和工具支持。

- **缺点**：
- `学习曲线较陡`，特别是对于新手，理解查询和变更的定义可能较复杂。
- `缓存机制更复杂`，通常需要额外的实现来支持缓存策略。
