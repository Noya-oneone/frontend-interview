# RESTful & GraphQL

## 一句话定位

* **RESTful**：以`资源`为中心的 API 风格 —— URL 表示资源、HTTP 方法表示操作，`服务端决定返回什么数据`。
* **GraphQL**：一种`查询语言 + 运行时` —— 单一端点，`客户端声明需要哪些字段`，服务端按查询返回。

## 核心对比

| 维度 | RESTful | GraphQL |
|--|--|--|
| 端点 | 多端点，每个资源一个 URL（`/api/v1/users/1`） | `单一端点`，POST 查询语句 |
| 数据获取 | 返回固定结构，常有`冗余字段（over-fetching）`或`需多次请求（under-fetching）` | 精确按需取字段，嵌套关联一次取全 |
| 错误表达 | HTTP 状态码语义化（404/500） | 通常一律 `200`，错误放响应体 `errors` 字段 |
| 版本管理 | 常需 `/v1 /v2` 版本控制 | 无需版本：新增字段不影响旧查询，废弃字段用 @deprecated |
| 缓存 | `HTTP 缓存机制直接可用`（GET + Cache-Control/ETag） | HTTP 缓存基本失效（POST + 动态查询），依赖客户端缓存 |
| 文档/类型 | 依赖 OpenAPI 等外部约定 | `Schema 强类型自文档化`，内省查询可自动生成文档 |

## RESTful 要点

* 语义化使用方法：`GET 读 / POST 建 / PUT 全量改 / PATCH 局部改 / DELETE 删`，配合状态码表达结果。
* 优点：简单、贴合 HTTP 原生语义、`缓存机制成熟`、生态与工具完善。
* 缺点：复杂嵌套数据要么多次请求、要么返回冗余；接口形态与前端需求耦合，版本维护成本高。

## GraphQL 要点

* 优点：一次请求取全所需、`不多不少`；强类型 Schema 便于协作与工具化；前端迭代不必等后端改接口。
* 缺点：`学习与服务端实现成本高`；缓存复杂；复杂查询可能压垮后端（需查询深度/复杂度限制）；文件上传、监控等生态不如 REST 顺手。
* 缓存实践：
  * 客户端库（`Apollo Client / Relay`）内置`规范化缓存`：按类型 + id 缓存实体，多组件复用、自动去重合并请求。
  * 想蹭 HTTP 缓存可用 `Persisted Queries`：查询预注册成哈希，请求转为 GET + 查询参数。

## 常见考点

* **什么时候选 GraphQL？** 多端（App/Web/小程序）字段需求差异大、页面聚合多个资源、前后端团队并行迭代快 —— BFF 场景尤其合适；简单 CRUD、重缓存的开放 API 用 REST 更划算。
* **GraphQL 全 200 怎么做监控告警？** 不能只看状态码，需解析响应体 errors 或在网关层统计业务错误率。
* **N+1 查询问题**：嵌套解析器逐条查库 —— 服务端用 DataLoader 批量合并解决。
