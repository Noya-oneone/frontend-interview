# 同源策略 

## 请求两次原因
* 页面刷新或重定向
* 预解析 DNS
* 浏览器自动发送 OPTIONS 请求（CORS 预检请求）
原理：当浏览器发起跨域请求时，如果请求方法是 PUT、DELETE 等非简单请求，或者请求头中包含自定义头部信息等情况，浏览器会先发送一个 OPTIONS 请求到服务器，询问服务器是否允许该跨域请求。只有当服务器返回允许的响应后，浏览器才会发送真正的请求。
示例：在一个前端项目中，前端代码使用 fetch 发起一个跨域的 PUT 请求：
```js
fetch('https://api.example.com/data', {
    method: 'PUT',
    headers: {
        'Content - Type': 'application/json',
        'Authorization': 'Bearer token123'
    },
    body: JSON.stringify({ key: 'value' })
});
```

* **同源策略** 是浏览器的核心安全功能之一，它限制了来自不同源的文档或脚本之间的交互。
所谓源，指的是一组**协议、域名和端口**的组合。

* 具体来说，如果两个URL的 *协议*、*域名*以及 *端口* 完全一致，那么它们就处于同一个源。
* 同源策略的主要目的是防止跨站脚本攻击（**XSS**）和跨站请求伪造（**CSRF**）等网络安全威胁，确保用户数据的安全性和隐私性。

## 跨域问题
### iframe
优点：跨域完毕之后DOM操作和互相之间的JavaScript调用都是没有问题的
缺点：1.若结果要以URL参数传递，这就意味着在结果数据量很大的时候需要分割传递，巨烦。2.还有一个是iframe本身带来的，母页面和iframe本身的交互本身就有安全性限制。
### script
优点：可以直接返回json格式的数据，方便处理
缺点：只接受GET请求方式

### 图片ping
优点：可以访问任何url，一般用来进行点击追踪，做页面分析常用的方法
缺点：不能访问响应文本，只能监听是否响应

### CORS
webpack 在 devServer 选项里面提供了一个 proxy 的参数供开发人员进行反向代理
然后再配合 http-proxy-middleware 插件对 api 请求地址进行代理
后再用 nginx 把允许跨域的源地址添加到报头里面即可
 
  * **CORS（Cross-Origin Resource Sharing）**： CORS实现起来非常方便,只需要增加一些HTTP头,让服务器能声明允许的访问来源,只要后端实现了CORS,就实现了跨域

  跨域资源共享（CORS）是浏览器的一种机制，它允许服务器声明哪些源可以访问资源。
  
  * 你可以通过配置 **Nginx** 以添加适当的 CORS 头部来解决跨域问题

  ```javascript
    add_header 'Access-Control-Allow-Origin' '*'; // 指定允许的源，可以设置为 * 允许所有源，或者设置为具体的域名
    add_header 'Access-Control-Allow-Methods' 'GET, POST, OPTIONS'; // 指定允许的 HTTP 方法
    add_header 'Access-Control-Allow-Headers' 'Origin, X-Requested-With, Content-Type, Accept'; //指定允许的请求头部，如 Content-Type, Authorization
    add_header 'Access-Control-Max-Age' 86400; // 指定预检请求（OPTIONS 请求）的缓存时间，以减少频繁的预检请求
  ```

  * **Proxy：** vue config js 配置proxy Nginx 也要配合配置

  ```javascript
      location /api/ {
        proxy_pass http://backend-server;
        proxy_redirect http://backend-server/ /api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
  ```

  * **服务器配置**

  ```javascript
  Access-Control-Allow-Origin: *
  Access-Control-Allow-Credentials: true
  ```

  #### 为什么会请求两次
  
  * 使用简单请求就不会出现这种情况了
  * 非简单请求的 CORS 请求，**会在正式通信之前，增加一次 HTTP 查询请求**，称为 **预检请求**。： 必须首先使用 **OPTIONS** 方法发起一个预检请求到服务器，以获知服务器是否允许该实际请求。

  * 在发送第一个请求时，如果请求触发了预检机制，浏览器会发送 `OPTIONS 请求`进行检查。
  * 之后，如果在预检响应的`缓存时间内`发送相同的请求，浏览器会使用缓存的预检结果，`避免重复发送预检请求`

  ### JSONP
  1、jsonp跨域(只能解决get） 原理：动态创建一个script标签。利用script标签的src属性不受同源策略限制，因为所有的src属性和href属性都不受同源策略的限制，可以请求第三方服务器资源内容
  利用h5新特性window.postMessage()
  * **JSONP：** JSONP 是通过动态创建 script 标签来实现跨域请求的。服务器会将数据放在一个回调函数的参数中返回，客户端可以通过这个回调函数来接收数据。
    * 只支持 GET 请求：JSONP 仅能通过 `<script> `标签发起 GET 请求，不支持其他 HTTP 方法（如 POST、PUT、DELETE）。
    * 由于 JSONP 返回的是 JavaScript 代码，因此服务器端返回的内容有可能被恶意利用。攻击者可以利用 JSONP 注入恶意代码。
    * 缺乏标准化：JSONP 是一种非标准的解决方案，可能不支持所有的浏览器特性和现代标准

    ```javascript
      <script>
          // 定义回调函数
          function handleResponse(data) {
              console.log('Received data:', data);
          }

          // 创建 JSONP 请求
          function makeJsonpRequest() {
              var script = document.createElement('script');
              script.src = 'https://api.example.com/data?callback=handleResponse';
              document.body.appendChild(script);
          }

          // 发起请求
          window.onload = makeJsonpRequest;
      </script>
    ```
