# 同源策略与跨域

## 同源策略

* 浏览器核心安全机制：限制不同`源`的文档/脚本之间的交互，防止恶意站点读取其他站点的数据。
* `源 = 协议 + 域名 + 端口`，三者完全一致才算同源。
* 限制范围：跨域 `XHR/fetch 读取响应`、跨域 DOM 访问、跨域 Cookie/Storage 读取。注意：`<img>`、`<script>`、`<link>` 等标签的资源`加载`本身不受限（JSONP 正是利用这一点）。

## 主流解决方案

### 1. CORS（标准方案）

服务器通过响应头声明允许哪些源访问：

```nginx
add_header 'Access-Control-Allow-Origin' 'https://www.example.com';  # 或 *
add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE, OPTIONS';
add_header 'Access-Control-Allow-Headers' 'Content-Type, Authorization';
add_header 'Access-Control-Max-Age' 86400;   # 预检结果缓存时间，减少 OPTIONS 请求
```

**简单请求 vs 预检请求（高频考点：为什么请求发了两次）**

* `简单请求`：方法为 GET/POST/HEAD，且头部只有安全白名单字段（Content-Type 限 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded`）→ 直接发送，浏览器只校验响应头。
* `非简单请求`（如 PUT/DELETE、`Content-Type: application/json`、自定义头 Authorization）→ 浏览器先发一个 `OPTIONS 预检请求`询问服务器是否允许，通过后才发真正请求。这就是 Network 里「同一个请求出现两次」的原因。
* 预检结果会按 `Access-Control-Max-Age` 缓存，有效期内相同请求不再预检。

**携带凭证的限制**：需要跨域带 Cookie 时，前端设 `credentials: 'include'`，服务端设 `Access-Control-Allow-Credentials: true`，且此时 `Allow-Origin 不能是 *`，必须是具体源。

### 2. 反向代理（开发与生产都常用）

利用「同源策略只限制浏览器」：让同源的服务器代为转发。

```js
// 开发环境：webpack/vite devServer proxy
devServer: {
  proxy: { '/api': { target: 'http://backend-server', changeOrigin: true } },
}
```

```nginx
# 生产环境：nginx 反向代理
location /api/ {
  proxy_pass http://backend-server/;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

### 3. JSONP（历史方案，只支持 GET）

利用 `<script src>` 不受同源限制：动态创建 script 标签，服务器返回 `callback(数据)` 形式的 JS 代码。

```js
function handleResponse(data) { console.log(data); }
const script = document.createElement('script');
script.src = 'https://api.example.com/data?callback=handleResponse';
document.body.appendChild(script);
```

缺点：只支持 GET、无错误处理机制、`存在 XSS 风险`（返回的是可执行代码，必须信任对方）—— 已被 CORS 全面取代，面试讲原理即可。

### 4. 其他手段

| 方案 | 适用场景 |
|--|--|
| `postMessage` | 跨域`页面/iframe 之间`通信的标准方案（见 [iframe](../0-HTML/<iframe>.md)） |
| `WebSocket` | 协议本身不受同源策略限制（服务端仍应校验 Origin） |
| `document.domain` | 仅限同一主域的子域间，已被浏览器逐步废弃 |
| 图片 ping（`new Image().src`） | 单向上报（打点统计），无法读响应 |

## 常见考点

* **同源策略防的是什么？** 防止恶意页面`读取`其他源的数据（如带着你的 Cookie 读银行接口响应）。注意 CSRF 防御主要靠 SameSite/token，同源策略挡不住「发送」。
* **为什么本地 file:// 或 localhost 调试遇到跨域？** localhost:3000 与 localhost:8080 端口不同即不同源 —— devServer proxy 就是为此而生。
* **OPTIONS 请求能省掉吗？** 让请求满足「简单请求」条件（如接口协商用表单编码），或配置 `Access-Control-Max-Age` 缓存预检结果。
* **CORS 报错但后端说加了头？** 常见坑：带 credentials 时 `Allow-Origin: *` 无效；预检 OPTIONS 请求本身没有被服务器正确响应（被鉴权中间件拦截返回 401）。
