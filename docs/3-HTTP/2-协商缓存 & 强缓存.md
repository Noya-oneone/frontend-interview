# 协商缓存 & 强缓存

浏览器缓存存储在本地（内存缓存 Memory Cache + 磁盘缓存 Disk Cache）。判断顺序：**先看强缓存，未命中或已过期再走协商缓存**。

## 强缓存（静态资源、CDN 资源、版本化文件）

* `不发请求`，直接使用本地缓存（DevTools 显示 `200 (from disk cache / memory cache)`）。
* 通过两个响应头控制，`Cache-Control 优先级高于 Expires`：
  * `Expires`（HTTP/1.0）：绝对过期时间，受客户端本地时钟影响。
  * `Cache-Control`（HTTP/1.1）：`max-age` 等指令控制，相对时间更可靠。

```
Cache-Control: max-age=31536000, immutable   // 缓存一年
Expires: Wed, 21 Oct 2026 07:28:00 GMT       // HTTP/1.0 兜底
```

* 优点：零请求，速度最快。缺点：有效期内`拿不到更新` —— 所以必须配合文件名哈希做「缓存失效」。

## 协商缓存（HTML、动态内容、API 响应）

* `每次都发请求`，带上验证信息，`由服务器决定`资源是否变化：没变返回 `304`（无 body，省流量），变了返回 200 + 新资源。

**两组配对头：**

| 组 | 服务器响应头 | 客户端下次请求头 | 判断依据 |
|--|--|--|--|
| 时间维度 | `Last-Modified`（最后修改时间） | `If-Modified-Since` | 修改时间是否更新（`秒级精度`） |
| 内容维度 | `ETag`（内容哈希/版本号） | `If-None-Match` | 标识是否一致（`更精确，优先级更高`） |

```
ETag: "abc123"                          → If-None-Match: "abc123"
Last-Modified: Tue, 20 Jul 2024 08:00:00 GMT → If-Modified-Since: 同值
```

* **为什么有了 Last-Modified 还要 ETag？**（高频追问）
  * 秒级精度不够：一秒内多次修改检测不到。
  * `修改时间变了但内容没变`（如重新部署 touch 了文件）会造成无谓的缓存失效。
  * 分布式服务器上的同一文件修改时间可能不一致。

## Cache-Control 常用指令

| 指令 | 行为 |
|--|--|
| `max-age=N` | N 秒内强缓存 |
| `no-cache` | `可以缓存但每次必须协商验证`（≠ 不缓存） |
| `no-store` | `真正的不缓存`，任何内容都不存 |
| `public / private` | 是否允许 CDN 等共享缓存存储 |
| `must-revalidate` | 过期后必须验证，不得使用陈旧副本 |
| `immutable` | 有效期内内容绝不改变，连刷新都不发验证请求 |

> 什么头都不给时，浏览器会用`启发式缓存`：按 `(当前时间 − Last-Modified) × 10%` 估算有效期 —— 这是「明明没配缓存却拿到旧资源」的常见原因。

## 工程实践：经典缓存策略

**HTML 不强缓存 + 静态资源哈希文件名强缓存**：

```nginx
# nginx：入口 HTML 永远协商
location ~* \.html$ {
  add_header Cache-Control "no-cache";
}
# 带哈希的静态资源缓存一年
location /assets/ {
  add_header Cache-Control "max-age=31536000, immutable";
}
```

```js
// webpack：内容变化 → 文件名变化 → 自动“失效”旧缓存
module.exports = {
  output: {
    filename: '[name].[contenthash].js',       // 用 contenthash 而非 hash
    chunkFilename: '[name].[contenthash].js',
  },
};
```

原理：HTML 每次协商拿最新，其中引用的资源名带 `contenthash` —— 内容不变命中一年强缓存；内容变了文件名变，等于换了个 URL，天然绕过旧缓存。这就是「版本号 `?v=2`」查询串方案的进化版。

## Service Worker 缓存（更灵活的一层）

Service Worker 位于页面与网络之间，可拦截请求实现任意缓存策略（cache-first、network-first、stale-while-revalidate），常配合 PWA 做离线能力：

```js
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('my-cache-v1').then((cache) => cache.addAll(['/', '/styles.css', '/script.js']))
  );
});

self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => cached || fetch(event.request))
  );
});
```

## 常见考点

* **from memory cache 和 from disk cache 的区别？** 内存缓存快、随标签页关闭清除（脚本、字体常驻内存）；磁盘缓存持久（图片、大文件多在磁盘）。刷新行为对两者的影响见 [刷新与强缓存](./2.0-刷新强缓存方法.md)。
* **no-cache 和 no-store？** no-cache = 缓存但必须验证；no-store = 完全不缓存。名字有误导性，必考。
* **强缓存期间服务器更新了怎么办？** 客户端感知不到 —— 这正是资源要带 contenthash、HTML 要 no-cache 的原因。
