
## Cookie 和 Session 的区别

* Cookie 和 Session 都用于管理用户的状态信息，例如用户的登录状态或用户偏好设置

| 特性 | Cookie | Session |
|-----|-----|---|
| **存储位置**| 存储在`客户端浏览器中`| 存储在服务器端|
| **存储大小**| 通常限制为 4KB| 受服务器内存限制 |
| **生命周期**| 由过期时间决定，可以是长期的 | 通常与用户会话相关，浏览器关闭后失效（可配置）|
| **安全性**| 易受 `XSS 攻击`，存储在客户端 | 较安全，不易受到客户端攻击 |
| **发送方式**| 每次 HTTP 请求时都会随请求发送 | 不随每次请求发送，仅通过 Session ID 识别 |
| **访问方式**| `客户端 JavaScript 可以访问`| 只能通过服务器访问 |
| **性能影响**| 大量 Cookie 会增加 HTTP 请求头的大小| 减少客户端数据负担，但增加服务器内存负担 |
| **使用场景**| 存储简单的、长期的数据，比如用户偏好| 存储复杂的、会话相关的数据，如登录状态|
| **跨域问题**| 可能需要设置 `SameSite` 和 `Domain` 属性| 不涉及跨域问题，完全在服务器端管理|


## 两者如何配合（高频追问）

典型登录流程：用户登录 → 服务器创建 Session（存服务器）→ 把 `Session ID 通过 Set-Cookie 下发` → 浏览器后续请求自动携带该 Cookie → 服务器凭 ID 找回会话数据。**Session 依赖 Cookie 做载体**（禁用 Cookie 时需 URL 重写等兜底）。

## Cookie 不安全为什么还要用

* `会话管理刚需`：HTTP 无状态，Cookie 让用户保持登录、购物车跨请求存续，且浏览器自动携带、无需前端代码干预。
* 安全短板可以`用属性补`：`HttpOnly` 防 JS 窃取、`Secure` 限 HTTPS、`SameSite` 防 CSRF（见 [Cookie & Storage](../2-JS/8-Cookie%20&%20storage%20&%20indexDB%20.md)）。
* 兼容性与生态最好，服务端框架的 Session 机制开箱即用。

## Session 的分布式问题（进阶）

多台服务器时内存 Session 不共享，方案：`Session 集中存储`（Redis，最常用）、负载均衡粘性会话（sticky session），或干脆改用`无状态 Token（JWT）`—— 服务器不存会话，凭证自带签名信息，代价是难以主动注销。
