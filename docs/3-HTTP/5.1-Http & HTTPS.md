# HTTP 和 HTTPS

## 核心区别

| 维度 | HTTP | HTTPS |
|--|--|--|
| 安全 | `明文传输`，可被窃听、篡改、中间人攻击 | TLS 加密，保证`机密性、完整性、身份认证` |
| 端口 | 80 | 443 |
| 证书 | 不需要 | 需要 CA 签发的数字证书（Let's Encrypt 等已可免费） |
| 性能 | 少一次 TLS 握手 | 多一次握手开销；TLS 1.3 已降到 1-RTT（会话复用 0-RTT），差距可忽略 |
| SEO / 能力 | 被浏览器标记「不安全」 | 搜索排名加权；`HTTP/2、Service Worker、Geolocation 等新能力仅 HTTPS 可用` |

HTTPS = HTTP + `TLS/SSL 安全层`（位于应用层与传输层之间），本质仍是 HTTP 语义。

## HTTPS 为什么安全：三种机制各司其职

| 目标 | 机制 |
|--|--|
| `机密性` | 数据传输用`对称加密`（如 AES） |
| `身份认证` | 证书 + `非对称加密`验证服务器身份，防假冒站点 |
| `完整性` | 摘要/消息认证码（MAC），篡改即校验失败 |

## 握手过程：非对称交换密钥，对称传输数据（高频考点）

1. **握手阶段（非对称加密）**
   * 服务器下发`数字证书`（含服务器公钥），客户端验证证书合法性（是否可信 CA 签发、域名匹配、未过期、未吊销）。
   * 双方协商生成`会话密钥`：经典 RSA 方式是客户端生成随机密钥用服务器公钥加密传去；现代 TLS 用 `ECDHE` 密钥交换（双方各出参数算出同一密钥，私钥泄露也不能解历史流量，即`前向安全`）。
2. **数据传输阶段（对称加密）**
   * 之后所有数据用会话密钥做`对称加密`传输。
   * 原因：`非对称加密计算量大`，只适合握手时少量数据；`对称加密效率高`，适合大流量 —— 两者结合兼顾安全与性能。

## 证书为什么可信：信任链

* 证书是 CA 用`CA 私钥`对「服务器公钥 + 域名等信息」的签名；浏览器内置根 CA 公钥，逐级验证签名 → `根证书 → 中间证书 → 站点证书`。
* 中间人无法伪造证书：没有 CA 私钥，签不出可通过验证的证书 —— 这解决了「公钥本身怎么防调包」的问题。

## 常见考点

* **对称加密用在哪？** 传输阶段的数据加密（AES）；握手阶段用非对称完成`身份认证与密钥交换`。
* **HTTPS 能防中间人吗？** 能，前提是证书验证不被绕过；用户手动信任非法证书（或设备被装了抓包根证书）则可被解密 —— 这正是 Charles/Fiddler 抓 HTTPS 的原理。
* **全站 HTTPS 后还要做什么？** `Strict-Transport-Security`（HSTS）响应头强制后续访问走 HTTPS，防降级攻击与首跳劫持。
