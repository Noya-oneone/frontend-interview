# JS 设计模式

* 设计模式的产生源于软件开发过程中对解决常见问题的经验总结(**前辈踩坑、后人乘凉**)，是软件设计中常用的一种`方法论`。
* 设计模式的提出和普及，使得软件工程师能够`共享经验`，提高软件开发的效率和质量，从而成为现代软件开发中的重要组成部分。

* 单一功能原则（Single Responsibility Principle）
* 开放封闭原则（Opened Closed Principle）

## 用处
* `软件复杂性的增加`：随着软件系统的规模和复杂性增加，开发人员需要有效的方法来组织代码，以便于维护和扩展。设计模式为开发人员提供了经过验证的、可复用的设计方案，帮助解决常见的设计问题。
* `代码复用的需求`：设计模式通过提供通用的设计解决方案，使得代码复用变得更加容易。它们提供了结构化的、可复用的代码模板，减少了开发中的重复劳动。
* `面向对象编程的普及`：随着面向对象编程（OOP）的普及，开发人员发现了一些在不同系统中反复出现的设计问题。设计模式为这些常见问题提供了解决方案，并且与OOP的概念（如封装、继承、多态）紧密结合。
* `沟通的需要`：设计模式为开发人员提供了一种共同的语言，使得团队成员可以更高效地沟通设计思想和解决方案。例如，当提到“单例模式”时，所有开发者都知道这意味着什么，从而避免了大量的解释工作。
* `软件质量的提升`：通过使用设计模式，开发人员可以创建更灵活、更易维护、更健壮的软件系统。设计模式帮助开发人员避免常见的设计错误，提升软件的可扩展性和可维护性。


## 设计模式的分类

设计模式 将 设计规则具体化，通常分为三大类：
* `创建型模式`：用于描述如何创建对象。
    * 单例模式
    * 工厂模式
    * 原型模式
* `结构型`： 用于描述如何组合对象以获得更大的结构。
    * 适配器模式
    * 组合模式
    * 装饰者模式
    * 门面模式
    * 享元模式
    * 适配者模式
* `行为型`： 用于描述对象之间相互作用的方式。 
    * 策略模式
    * 观察者模式
    * 发布订阅模式
    * 命令模式
    * 状态模式
    * 模板模式
    * 职责链模式
    * 中介模式
    * 迭代器模式

- **单例模式**
  - 定义：确保**一个类只有一个实例**，并提供全局访问点。
  - 优点：节省资源，全局共享数据。
  - 缺点：难以测试，隐藏依赖。
  - 适用场景：`Redux` 和 `Vuex` 的 `store`，整个应用中只存在一个 `store` 实例。

- **工厂模式**
  - 定义：提供一个创建对象的接口，而不指定具体类。
  - 优点：封装实例化逻辑，易于扩展。
  - 缺点：增加代码复杂性，可能**导致过多的子类**。
  - 适用场景：React 的 `createElement` 方法，用于创建组件实例。

- **原型模式**
  - 定义：用原型实例指定创建对象的种类，并且通过拷贝这些原型创建新的对象。
  - 优点：简化创建复杂对象，避免构造函数的复杂度。
  - 缺点：性能问题，容易产生**对象过多**。
  - 适用场景：`JavaScript` 中的 `Object.create()` 方法，`Vue.js` 的 `data` 选项。

- **策略模式**
  - 定义：定义一系列算法，将每个算法封装起来，并使它们可以相互替换。
  - 优点：易于扩展和维护，不同策略独立。
  - 缺点：可能增加系统复杂度，客户端**必须了解不同策略**。
  - 适用场景：React.js 的 `Fiber 调度算法`，依据不同情况选择调度策略。

- **观察者模式**
  - 定义：定义对象间的一对多依赖，当一个对象改变状态时，所有依赖它的对象都会收到通知并自动更新。
  - 优点：实现松耦合，自动更新数据。
  - 缺点：可能引发**性能问题，复杂的依赖关系**。
  - 适用场景：Vue.js 的`响应式数据绑定`，自动更新依赖数据。

- **发布订阅模式**
  - 定义：定义一对多的依赖关系，当一个对象发生状态变化时，所有依赖它的对象都将得到通知。
  - 优点：解耦，降低耦合度，简化代码。
  - 缺点：可能引发**性能问题，消息订阅和发布的性能开销**。
  - 适用场景：`React.js` 的 `Context API`，`Vue.js` 的 `Vuex`。

- **装饰者模式**
  - 定义：动态地为对象添加行为或职责，而不改变其接口。
  - 优点：灵活扩展对象功能，遵循开闭原则。
  - 缺点：**增加系统复杂度**，可能导致过多的装饰者。
  - 适用场景：React 中的高阶组件`（HOC）`，Vue 中的混入`（mixins）`。

- **代理模式**
  - 定义：为其他对象提供一个代理以控制对这个对象的访问。
  - 优点：控制对象访问，延迟初始化，减少内存开销。
  - 缺点：**增加代码复杂度，性能开销**。
  - 适用场景：Vue.js 的响应式数据代理，通过 `Proxy` 实现响应式。

- **门面模式**
  - 定义：为子系统中的一组接口提供一个统一的接口，简化系统的使用。
  - 优点：简化接口，降低客户端对子系统的依赖。
  - 缺点：**不符合开闭原则，可能导致过多的门面接口**。
  - 适用场景：`Vue.js 的 API` 设计，通过简单 API 隐藏内部复杂性。

- **模板方法模式** 父类中定好执行顺序，子类可以不改变结构即可重定义算法的某些特定步骤。
  - 定义：定义一个操作中的算法骨架，将一些步骤延迟到子类中，使得子类可以不改变算法结构即可重定义算法的某些特定步骤。
  - 优点：提高代码复用，封装变化，提高可扩展性。
  - 缺点：增加系统复杂度，可能导致**多层继承**。
  - 适用场景：React.js 的 `生命周期`，Vue.js 的 `生命周期`。
