# 性能优化与内存泄漏排查

## 核心概念

Node 服务的性能问题基本落在两类：**事件循环被阻塞（CPU）** 和 **对象被意外持有（内存）**。

排查的关键是**先量化再动手**——用 `perf_hooks`、堆快照、火焰图定位到具体代码，而不是凭感觉加缓存。面试中最能体现深度的是 **能说出用什么工具、怎么读结果**。

## 详解

### 1. 常见内存泄漏来源

| 来源 | 说明 |
|------|------|
| **全局变量 / 模块级缓存** | 只增不减的 `Map`、数组，随请求量无限增长 |
| **未移除的事件监听** | `emitter.on` 反复注册，超过 10 个会有 `MaxListenersExceededWarning` |
| **闭包持有大对象** | 回调捕获了整个请求上下文 |
| **未清理的定时器** | `setInterval` 未 `clearInterval`，回调链上的对象全部存活 |
| **Promise 永不 settle** | 挂起的 Promise 及其闭包无法回收 |

### 2. 用 WeakMap / WeakRef 避免持有

缓存以对象为 key 时，用 **`WeakMap`** 让 key 被回收后条目自动消失：

```js
// 泄漏：req 对象被 Map 永久持有
const cache = new Map();
cache.set(req, computeSomething(req));

// 安全：req 无其他引用时，条目自动被 GC
const cache = new WeakMap();
cache.set(req, computeSomething(req));
```

### 3. 定位内存泄漏：堆快照对比

核心方法是 **三次快照法**：

1. 服务启动后打一次基线快照
2. 施加压力（跑一轮压测）
3. 手动触发 GC 后再打一次快照
4. 在 Chrome DevTools 的 **Comparison 视图**里看哪类对象 `Delta` 持续为正

```bash
# 启动时开启 inspector，Chrome 访问 chrome://inspect 连接
node --inspect server.js

# 或在代码里主动写快照
node --expose-gc server.js
```

```js
import { writeHeapSnapshot } from 'node:v8';

process.on('SIGUSR2', () => {
  // 收到信号时落盘，用 kill -USR2 <pid> 触发
  const file = writeHeapSnapshot();
  console.log(`堆快照已写入 ${file}`);
});
```

### 4. 定位 CPU 瓶颈：火焰图

```bash
# 内置 profiler，生成 isolate-*.log
node --prof server.js
node --prof-process isolate-*.log > profile.txt

# 更直观：clinic 火焰图
npx clinic flame -- node server.js
npx clinic doctor -- node server.js   # 自动诊断阻塞/GC/I-O 问题
```

火焰图里**横条越宽 = 占用 CPU 时间越长**，顶部的宽平台就是热点函数。

### 5. 监控事件循环延迟

事件循环延迟是 Node 服务最重要的健康指标——**它上升说明主线程被阻塞**：

```js
import { monitorEventLoopDelay } from 'node:perf_hooks';

const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();

setInterval(() => {
  // 单位是纳秒，转成毫秒更直观
  console.log({
    mean: h.mean / 1e6,
    p99: h.percentile(99) / 1e6,
  });
  h.reset();
}, 10_000);
```

> 经验值：**p99 超过 100ms 就说明有明显阻塞**，需要排查同步代码或大对象序列化。

### 6. 其他常见优化点

- **避免同步 API**：`fs.readFileSync`、`crypto.pbkdf2Sync` 在请求路径上会直接堵死主线程
- **`JSON.parse/stringify` 是同步的**：大对象序列化同样阻塞，考虑流式 JSON
- **提高线程池上限**：I/O 密集场景可调 `UV_THREADPOOL_SIZE`（默认 4）
- **开启 gzip/brotli**：见 [Performance-GZIP](../2-Performance-GZIP.md)
- **连接复用**：设置 `http.Agent` 的 `keepAlive: true`，避免反复 TCP 握手

## 常见考点

- 问题 1：怎么定位 Node 内存泄漏？→ **三次堆快照对比**，看 Delta 持续为正的对象类型
- 问题 2：怎么定位 CPU 飙高？→ `--prof` / `clinic flame` 生成火焰图找热点函数
- 问题 3：Map 和 WeakMap 在缓存场景怎么选？→ **key 是对象且生命周期由外部决定时用 WeakMap**
- 问题 4：衡量 Node 服务健康度最关键的指标？→ **事件循环延迟（p99）**
- 问题 5：为什么线上不建议用同步 API？→ 阻塞主线程，所有并发请求一起被拖慢

## 代码示例

一个会泄漏的缓存，以及修好的版本：

```ts
// ❌ 泄漏版：cache 只增不减，QPS 越高涨得越快
const cache = new Map<string, Buffer>();

async function getAvatar(userId: string): Promise<Buffer> {
  if (cache.has(userId)) return cache.get(userId)!;
  const data = await downloadAvatar(userId);
  cache.set(userId, data); // 永远不删
  return data;
}
```

```ts
// ✅ 修复版：容量上限 + LRU 淘汰
const MAX_ENTRIES = 500;
const cache = new Map<string, Buffer>();

async function getAvatar(userId: string): Promise<Buffer> {
  const cached = cache.get(userId);
  if (cached) {
    // 命中后重新插入，维持「最近使用在末尾」的顺序
    cache.delete(userId);
    cache.set(userId, cached);
    return cached;
  }

  const data = await downloadAvatar(userId);
  cache.set(userId, data);

  // Map 迭代顺序即插入顺序，首个 key 就是最久未使用的
  if (cache.size > MAX_ENTRIES) {
    const oldest = cache.keys().next().value;
    if (oldest !== undefined) cache.delete(oldest);
  }

  return data;
}
```
