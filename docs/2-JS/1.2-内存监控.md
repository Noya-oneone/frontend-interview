# 内存监控

## 内存泄漏

程序运行中，`不再需要的内存因引用未释放而无法回收`，占用持续增长，最终导致页面卡顿甚至崩溃。

判断思路：**内存曲线只涨不落**（做完操作、手动触发 GC 后仍回不到基线）基本就是泄漏。

## Performance 面板：先看趋势

录制时勾选 Memory，重点看这几条曲线：

| 指标 | 含义 | 关注点 |
|--|--|--|
| `JS Heap` | JS 对象、函数等动态分配的堆内存 | 反复执行同一操作后是否阶梯式上涨 |
| `Documents` | 内存中的文档对象数量 | iframe 打开又关闭后是否回落（detached document） |
| `Nodes` | 内存中的 DOM 节点数 | 列表增删后节点数是否回落（游离节点） |
| `Listeners` | 注册的事件监听器数量 | 组件销毁后监听数是否回落 |
| `GPU Memory` | 图片、视频、WebGL 等占用的显存 | 大量图像/WebGL 场景 |

## Memory 面板：定位泄漏点

堆快照（Heap Snapshot）三个关键列：

* `Distance`：对象到`根对象（如 window）的最短引用路径长度`。异常地近说明被全局直接持有。
* `Shallow Size`：对象`自身`占用的内存，不含它引用的其他对象。大字符串、大数组的 Shallow Size 大。
* `Retained Size`：`回收该对象后能连带释放的总内存`（自身 + 只能经它访问的所有对象）。**排查泄漏看这一列** —— Retained Size 大的对象是「堵住」内存的闸门。

实用手法：

* `对比快照`：操作前拍一张、操作后拍一张，用 Comparison 视图看新增对象是谁创建的。
* 搜索 `Detached` 可找到脱离 DOM 树但仍被引用的游离节点。
* `Allocation instrumentation on timeline` 记录分配时间线，蓝色柱（未释放）对应的调用栈就是泄漏源头。

## 其他工具

* `performance.memory`（Chrome）/ `performance.measureUserAgentSpecificMemory()`：代码内粗粒度监控，可用于线上上报。
* Node.js：`process.memoryUsage()` 查看 rss / heapUsed；`--inspect` 后同样用 DevTools 拍堆快照；`heapdump` 生成线上快照。

## 常见考点

* **Shallow Size 和 Retained Size 的区别？** 自身占用 vs 回收后可连带释放的总量；泄漏排查看 Retained。
* **常见泄漏源？** 意外全局变量、未清理的定时器与事件监听、游离 DOM 节点引用、闭包长期持有大对象（见 [垃圾回收](./1.1-浏览器的垃圾回收机制.md)、[闭包](./1.1-闭包.md)）。
* **怎么在测试中稳定复现泄漏？** 重复执行「进入 → 操作 → 退出」N 次，拍快照对比同类对象数量是否线性增长。
