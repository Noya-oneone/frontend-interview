# 浏览器的垃圾回收机制

## 核心概念

* 垃圾回收（Garbage Collection, GC）`自动检测并释放不再使用的内存`，防止内存泄漏。
* 判断「垃圾」的标准：对象从`根（全局对象、当前调用栈上的局部变量等）出发不可达`。

## 两种基础算法

### 标记-清除（Mark-and-Sweep）—— 现代引擎的基础

* `标记阶段`：从根对象出发，`递归遍历所有可达对象`并打标记。
* `清除阶段`：未被标记的对象视为不可达，释放其内存。
* 优点：能正确处理`循环引用`（互相引用但整体不可达的对象照样回收）。
* 缺点：回收后产生`内存碎片`；朴素实现需要`暂停程序（Stop-The-World）`，对象多时停顿明显。
* 补充：`标记-整理（Mark-Compact）`在清除后把存活对象`移动归拢`，消除碎片，代价是移动对象更耗时。

### 引用计数（Reference Counting）—— 历史方案

* 记录每个对象被引用的次数，`归零即回收`。
* 致命缺陷：`无法处理循环引用` —— 两个互相引用的对象计数永不为零，导致泄漏（老 IE 的 DOM 与 JS 之间曾用此法，是经典泄漏源）。现代 JS 引擎`不用它做主 GC`。

## V8 的优化策略（面试深入点）

V8 采用`分代式垃圾回收`：绝大多数对象「朝生夕死」，按存活时间分区管理。

| | 新生代（Young） | 老生代（Old） |
|--|--|--|
| 存放 | 新创建的小对象 | 存活多次回收的对象、大对象 |
| 算法 | `Scavenge（半空间复制）`：内存对半分为 From/To，存活对象复制到 To 后整体交换 | `标记-清除 + 标记-整理` |
| 频率 | 高频、极快 | 低频、更彻底 |
| 晋升 | 经历一次回收仍存活、或 To 空间占用超阈值 → 移入老生代 | — |

降低停顿的三项技术：

* `增量回收（Incremental）`：把标记拆成小步，穿插在 JS 执行间隙。
* `并发回收（Concurrent）`：标记工作放到辅助线程，与主线程同时进行。
* `惰性清理（Lazy Sweeping）`：按需分批清理，而非一次清完。

## 常见内存泄漏场景

* 意外的全局变量（未声明直接赋值）
* 被遗忘的定时器 / 事件监听器（组件销毁未 clear / removeEventListener）
* 脱离 DOM 树但仍被 JS 变量引用的节点
* 闭包长期持有大对象（详见 [闭包](./1.1-闭包.md)、[内存监控](./1.2-内存监控.md)）

## 常见考点

* **循环引用会泄漏吗？** 标记-清除下不会 —— 只要整体不可达就能回收；引用计数才有这个问题。
* **WeakMap / WeakSet 与 GC 的关系？** 它们对键（值）是`弱引用`，不阻止回收，适合做元数据缓存（见 [数据类型](./3-数据类型%20.md)）。
* **手动触发 GC？** JS 无法手动触发；只能通过解除引用（置 null、删除监听）让对象变得不可达。
